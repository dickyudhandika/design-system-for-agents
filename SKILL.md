# Design System for Agents (ds4a)

A portable taste layer for AI coding agents. Three commands power the full
loop: `ds4a init` → build → `ds4a review` → `ds4a merge`. The library compounds
with every project.

## Commands

| Command | What happens |
|---|---|
| `ds4a init [type]` | Detect baseline → install/convert → generate DESIGN.md + dev playground → launch preview |
| *(build normally)* | Agent reads DESIGN.md, generates UI. Skill stays out. |
| `ds4a review` | Three-pass analysis on generated code. Interactive approve/reject. |
| `ds4a merge` | Merge approved rules into `.ds4a/library.md` in-place. |
| `ds4a preview` | Open `preview/index.html` in the browser — live showcase of the 13 core contracts. |

All commands are explicit — the developer types them. No auto-triggering.

## File Structure

```
project/
├── [existing files — untouched, never modified]
├── DESIGN.md                                 ← generated by ds4a init, lives in project root
├── .ds4a/
│   ├── library.md                            ← master library, updated in-place on merge
│   └── preview.html                          ← offline static playground fallback
├── src/
│   ├── lib/
│   │   └── design-tokens.ts                  ← single source of truth for tokens
│   ├── styles/
│   │   ├── tokens.generated.css              ← compiled @theme definitions
│   │   └── global.css                        ← imports tokens.generated.css
│   ├── components/design-system/
│   │   └── DesignSystemExplorer.tsx          ← canonical interactive playground
│   └── pages/
│       └── design-system.astro               ← dev-only route (http://localhost:4321/design-system)
└── scripts/
    └── build-tokens.ts                       ← token synchronization compiler
```

Non-destructive: DESIGN.md sits alongside existing files. AGENTS.md,
tokens.css, tailwind.config.js — all untouched. The skill reads them for
conversion but never overwrites.

State: re-detect from files each session. `.ds4a/library.md` exists =
initialized. `DESIGN.md` exists = generated. No state file needed.

## Phase 1+2: `ds4a init [type]`

Combined init + generate. One command. Explicit trigger.

### Step 1: Detect baseline (auto)

Check project root for existing design system:

```
1. .ds4a/library.md exists? → already initialized → skip to Step 3 (generate)
2. DESIGN.md exists? → already has one → skip to Step 3 (generate)
3. AGENTS.md exists? → scenario B (has rules + maybe tokens)
4. globals.css has shadcn vars (`--background`, `--primary`)? → scenario D (shadcn baseline)
5. design-tokens.ts / tokens.ts / tokens.generated.css exists? → scenario E (modern typed/Tailwind v4 pipeline)
6. globals.css / style.css has Tailwind v4 `@theme` block? → scenario E (Tailwind v4 baseline)
7. tokens.css / tokens.json exists? → scenario C (has tokens, no rules)
8. tailwind.config.js/ts exists? → scenario C (has config, extract)
9. None of the above → scenario A (no baseline)
```

### Step 2: Install or convert (based on scenario)

**Scenario A — no baseline:**
1. Copy `references/master-library.md` to `.ds4a/library.md`
2. This is the curated default: sharp-edge warm-white aesthetic, 13 core
   component contracts (see `references/core-components.md`), 44 guardrails,
   10-item pre-flight checklist
3. Report: "No design system found. Installed curated baseline (sharp-edge
   warm-white, 13 core contracts)."

**Scenario B — has AGENTS.md:**
1. Read AGENTS.md for rules + guardrails
2. Read tokens.json/tokens.css for token values (if present)
3. **DISCREPANCY CHECK (critical):** Grep AGENTS.md for stale values. Common
   drift: color name ("mint" vs "blue"), radius values (4/8/16px vs 0px),
   legacy token names (font-size-body vs label-md). tokens.json is source of
   truth for values. Fix prose to match.
4. Convert to DESIGN.md format:
   - tokens.json → YAML frontmatter
   - AGENTS.md rules → 8 canonical prose sections (Overview, Colors,
     Typography, Layout, Elevation & Depth, Shapes, Components, Do's and
     Don'ts)
   - Add missing sections: Overview (design personality), Pre-flight
     Checklist (10 items)
5. Write converted library to `.ds4a/library.md`
6. Report: "Found AGENTS.md. Converted to DESIGN.md format. [N] discrepancies
   fixed."

**Scenario C — has tokens, no rules:**
1. Read tokens from CSS variables (`:root { --color-*: ... }`) or
   tailwind.config.js
2. Convert tokens to DESIGN.md YAML frontmatter
3. Generate guardrails from token patterns:
   - If color.primary exists → "primary for CTAs and active states only"
   - If color.destructive exists → "destructive for errors only"
   - If radius all 0px → "sharp edges, deliberate aesthetic choice"
   - If spacing scale exists → "4px base unit, use the scale"
4. Write generated library to `.ds4a/library.md`
5. Report: "Found tokens but no rules. Extracted [N] tokens, generated
   [M] guardrails. Review and adjust."

**Scenario D — shadcn/ui baseline (user-customized theme):**
The user's shadcn theme (customized at https://ui.shadcn.com/create or in
`globals.css`) is the foundation. ds4a imports it — never overwrites.

1. Read `globals.css` → extract `:root` (light) + `.dark` blocks
2. Convert `oklch()` → hex with `scripts/oklch-to-hex.py`
   (`cat globals.css | python3 scripts/oklch-to-hex.py`)
3. Map shadcn vars → ds4a YAML frontmatter (see
   `references/shadcn-baseline.md` for the full mapping table)
4. Generate guardrails from imported theme patterns (Scenario C logic:
   radius → sharp/rounded rule, primary → action-only rule, etc.)
5. Run AA contrast check on `muted-foreground` vs `background`. Flag if
   it fails.
6. Write imported library to `.ds4a/library.md`
7. Report: "Found shadcn theme. Imported [N] tokens from globals.css.
   [M] guardrails generated. Contrast check: [pass/fail]."

**Scenario E — Modern Typed Tokens & Tailwind v4 `@theme` Pipeline:**
For projects with interactive documentation, design system explorers, or Tailwind v4:
1. Identify the Source of Truth:
   - If `src/lib/design-tokens.ts` (or `tokens.ts`) exists: TypeScript token registry is the single source of truth for values, categories, roles, and WCAG metadata.
   - If `tokens.generated.css` or `@theme` exists: Tailwind v4 consumes pure CSS variables generated from the typed layer.
2. Verify / Establish the Token Sync Pipeline:
   - Tokens defined in TypeScript/JSON.
   - A lightweight generator script (e.g. `scripts/build-tokens.ts`) compiles TS tokens into `tokens.generated.css` declaring `@theme { ... }`.
   - `global.css` imports the generated tokens via `@import "./tokens.generated.css";`.
   - Explorer / documentation components import the TS tokens directly for live interactive previews and contrast checking.
3. Convert tokens to DESIGN.md YAML frontmatter:
   - Extract colors, typography scales, font families, radius caps, and spacing.
   - Preserve rich metadata (WCAG notes, roles, usage rules) in section prose.
4. Generate guardrails:
   - Set `source-of-truth: src/lib/design-tokens.ts` in library frontmatter.
   - Document zero-drift rule: all token edits occur in the TS source; CSS is an auto-generated build artifact.
5. Write generated library to `.ds4a/library.md`.
6. Report: "Found modern typed token pipeline. Imported [N] tokens from design-tokens.ts with Tailwind v4 @theme integration. Zero-drift pipeline verified."

**For all scenarios:**
- Never touch existing files (AGENTS.md, tokens.css, globals.css,
  tailwind.config.js)
- Only create new files: `.ds4a/library.md` and `DESIGN.md`

### Step 3: Generate project DESIGN.md

This step runs automatically after install/convert — `ds4a init` does both.

1. Read `.ds4a/library.md` (the master library)
2. Accept project type from the command:
   - `ds4a init dashboard` → type = "dashboard"
   - `ds4a init landing-page` → type = "landing-page"
   - `ds4a init auth-flow` → type = "auth-flow"
   - If no type given → ask: "What are you building? (dashboard, landing-page,
     auth-flow, settings, data-table, content-site, e-commerce, admin-panel)"
3. Read `references/component-matrix.md` for relevance + layout matrices
4. Apply extraction rules:

   **ALWAYS include:**
   - Full YAML frontmatter (all tokens)
   - Overview section
   - Colors section (all rules)
   - Typography section (all rules + size scale)
   - Shapes section (radius + rationale)
   - Do's and Don'ts (all guardrails)
   - Pre-flight Checklist (all items)

   **INCLUDE if relevant (from matrix):**
   - Component contracts (only for components this project type uses)
   - Layout rules (sidebar for dashboard, hero for landing-page, etc.)
   - Elevation & Depth (if project uses cards/modals/popovers)
   - Motion (if project has interactive elements)

   **EXCLUDE:**
   - Component contracts for unused components
   - Irrelevant layout rules
   - Component-specific guidance not relevant to project type

5. Size constraint: output should be 30-50% of master library
6. Write generated DESIGN.md to project root
7. Report: "Project DESIGN.md generated. [N] lines, [X]% of master. Includes:
   [list of component contracts included]."

### Step 4: Verify

After writing both files, verify:
- `.ds4a/library.md` exists and has valid YAML frontmatter
- `DESIGN.md` exists and has all required sections
- All token values from source (if scenario B/C) are preserved
- No stale references in converted files

### Step 5: Scaffold Canonical `/design-system` Route & Loop In User

Taste is visual. Never leave the user reading only markdown tables. Generate the live interactive explorer matching the canonical `http://localhost:4321/design-system` structure:

1. **Scaffold the Single Source of Truth Pipeline:**
   - Create `src/lib/design-tokens.ts`: exports `COLOR_TOKENS`, `TYPOGRAPHY_TOKENS`, `SPACING_TOKENS`, `RADIUS_TOKENS`, and `PRINCIPLES`.
   - Create `scripts/build-tokens.ts`: compiles tokens into `src/styles/tokens.generated.css` declaring `@theme { ... }`.
   - Update `src/styles/global.css`: imports `@import "./tokens.generated.css";`.
   - Bind lifecycle hooks in `package.json`: `"predev": "node scripts/build-tokens.ts"`, `"prebuild": "node scripts/build-tokens.ts"`.

2. **Scaffold the In-Framework Dev-Only Route (`/design-system`):**
   - File: `src/pages/design-system.astro` (or Next.js / SvelteKit equivalent from `templates/design-system-page.astro`).
   - **Dev-only gate:** `if (!import.meta.env.DEV) return Astro.redirect('/');` (in production builds, compiles a safe redirect with noindex).
   - **Header Specimen:**
     - Brand kicker (`<Brand> · Design System`) + dev-only pill badge.
     - Headline with `text-balance` leading into single-source-of-truth description.
     - 4-column `<dl>` stat counters (`Colors`, `Type styles`, `Spacing steps`, `Radii`) with `tabular-nums`.

3. **Scaffold the Interactive Explorer Component (`DesignSystemExplorer`):**
   - File: `src/components/design-system/DesignSystemExplorer.tsx` (from `templates/DesignSystemExplorer.tsx`).
   - **Sticky Nav Bar:** Tabs for `Principles`, `Color`, `Typography`, `Spacing`, `Radius`, `Components`, and `Theme code`.
   - **Search Bar:** Real-time token filter by name, role, hex, or CSS variable.
   - **Principles Section:** Highlights key architectural boundaries (e.g. 2-tone palette, 8px radius ceiling, 500 font-weight ceiling).
   - **Color Grid:** Grouped into `Surfaces`, `Neutrals`, `Brand`, and `States`. Displays live contrast ratios against canvas ground (AA/AAA pass/fail badges), role explanations, and click-to-copy tokens.
   - **Typography Specimen:** Displays all paired fonts (Display, Sans, Mono) with relative `em` letter-spacing, uppercase badges, line-heights, and a live editable text input.
   - **Spacing Visualizer:** Bars displaying the project's exact spacing scale (px and rem values).
   - **Radius Cards:** Visual cards demonstrating the exact radius constraint (e.g. 8px max, sharp edges, no pills).
   - **Components Sandbox:** Primitives including Buttons (Primary, Outline, Ghost with active states), Form Inputs (with 16px mobile compliance check), Badges, and Modal specimens.
   - **Theme Code Exporter:** Ready-to-copy `@theme` block generated directly from tokens without drift.

4. **Generate Offline Fallback (`.ds4a/preview.html`):**
   - Self-contained static version saved to `.ds4a/preview.html` for environments without a running dev server.

5. **Loop in the user:**
   - Report:
     ```
     ✓ Project DESIGN.md generated ([N] lines).
     ✓ Dev-only interactive route created at /design-system
     ✓ Offline playground created at .ds4a/preview.html
     → Launching http://localhost:4321/design-system in browser...
     ```
   - Automatically trigger `ds4a preview` so the user gets that immediate visual confirmation of the v1 design system.

## Phase 3: Build (no skill action)

The skill does nothing here. The AI agent reads DESIGN.md and builds UI
following the tokens, guardrails, and component contracts.

If a component needed by the project isn't in the DESIGN.md, the agent
builds it following the design system rules (tokens, guardrails, aesthetic).
This is expected — it's how the library grows. The review phase catches the
new component and suggests it as a contract.

## Phase 6: `ds4a preview`

Opens the canonical interactive design system explorer (`http://localhost:<port>/design-system`) in the default browser. Triggered explicitly or automatically at the end of `ds4a init`.

1. **Active Dev Server Detection (Preferred):**
   - Checks if a dev server is running on common ports (`4321` for Astro, `3000` for Next.js, `5173` for Vite).
   - If active and `/design-system` route exists, launches `http://localhost:<port>/design-system`:
     `open http://localhost:4321/design-system` (macOS) / `xdg-open` (Linux).
   - Benefits: Renders with the project's actual web fonts, Tailwind v4 compiler, Preact/React hydration, and layout reset.

2. **Offline Static Fallback:**
   - If no dev server is active or running in a headless CI environment, opens `.ds4a/preview.html`:
     `open .ds4a/preview.html` (macOS) / `xdg-open` (Linux).
   - Prints a friendly helper tip: `Tip: Run 'npm run dev' to see the full living specimen at http://localhost:<port>/design-system`.

3. **Guarantees:**
   - **Dev-Only:** Gated via `import.meta.env.DEV` redirect; 100% prevented from shipping in production builds.
   - **Zero Drift:** Direct consumer of `src/lib/design-tokens.ts` and compiled `@theme` CSS.
   - **Full Interactivity:** Principles, searchable color cards with live contrast audits, live editable typography specimen, spacing bars, radius cards, and component sandboxes.

## Phase 4: `ds4a review`

Explicit trigger. Three-pass analysis on generated code.

### Step 1: Read inputs

1. Read generated code files:
   - `src/**/*.{tsx,jsx,vue,svelte,html,css}`
   - `app/**/*.{tsx,jsx}`
   - `pages/**/*.{tsx,jsx,astro}`
   - `components/**/*.{tsx,jsx,vue,svelte}`
   - Or whatever directory pattern matches the project structure
2. Read the project `DESIGN.md`

### Step 2: Run three-pass analysis

Load `references/review-prompt.md` for the full review architecture. Execute
the three passes:

**Pass 1: Violation Detection**
- Check generated code against existing rules in DESIGN.md
- For each violation: cite exact rule, cite file:line, describe discrepancy
- Scan checklist: tokens (hex colors, spacing, font sizes, radius, shadows),
  layout rules (grid patterns, section gaps, max-widths), guardrails (primary
  count per screen, H1 count, disabled state method, placeholder color)

**Pass 2: Pattern Detection**
- Find repeated decisions not yet codified in DESIGN.md
- Count occurrences, list every file:line
- Suggest as new rule only if 3+ times consistent
- Patterns to find: spacing, color, typography, component, layout, state

**Pass 3: Gap Detection**
- Find where AI guessed with no guidance from DESIGN.md
- If consistent → suggest as new rule
- If inconsistent → suggest as guardrail
- Check: component types not covered, responsive breakpoints, animation
  values, layout patterns, error/loading/empty states

**Promotion check (tier mechanics — see `references/core-components.md`):**
- A `(grown)` contract included in 3+ separate project DESIGN.md generations
  → output promotion suggestion: `Promote [X] to core? [y/n]`
- On yes (at merge): remove `(grown)` marker, add to core list

### Step 3: Apply quality filter

Every suggestion must pass ALL 5 checks:
1. **Specific** — exact value, structure, behavior. No "consistent," "clean,"
   "spacious" — discard.
2. **Applicable** — directly pasteable into DESIGN.md. If needs explanation —
   discard.
3. **Preventive** — prevents a specific mistake next time. If just
   observational — discard.
4. **Taste-matched** — aligns with Overview + Do's/Don'ts. If contradicts
   aesthetic — discard silently.
5. **Evidence-backed** — can point to specific file:line. If not — discard.

### Step 4: Output suggestions

For each suggestion, output in the structured format (see
`references/review-prompt.md` for exact format). Output violations first, then
patterns (high → medium → low confidence), then gaps. End with review
summary.

### Step 5: Interactive approval

Present each suggestion to the developer:
```
Suggestion 1/5: card-padding-default (token, high confidence)
  spacing.card.padding: 24px — 6 occurrences across 6 files
  Approve? [y/n]:
```

Collect approved and rejected lists. Store in memory for `ds4a merge`.

## Phase 5: `ds4a merge`

Explicit trigger. Merge approved rules into `.ds4a/library.md` in-place.

### Step 1: Read approved suggestions

From the review phase, collect all approved suggestions. If no review was
run recently, ask: "No recent review found. Run `ds4a review` first."

### Step 2: Merge each approved rule

For each approved suggestion, determine type and insert location:

| Type | Insert location | Method |
|---|---|---|
| token | YAML frontmatter | Add line under appropriate category |
| prose-rule | Relevant `##` section | Add under appropriate subsection |
| guardrail | `## Do's and Don'ts` | Add ✅ Do or ❌ Don't line |
| component-contract | `## Components` | Add new `###` subsection |

**Tier marker:** a new component-contract added by merge gets `(grown)` in its
header: `### Checkbox (grown)`. Core contracts never get the marker. Promotion
(see Phase 4) removes the `(grown)` marker and adds the component to the core
list in the library's component inventory.

**Merge rules:**
- Insert in-place — no new files, no version copies
- Increment `version` in YAML frontmatter (e.g., `version: 2` → `version: 3`)
- Preserve all existing content — only add, never remove
- If a suggestion conflicts with an existing rule, skip it and note:
  "Skipped: conflicts with existing rule [name]."

### Step 3: Verify merge

After merging:
- YAML frontmatter still parses
- No duplicate rules added
- Version incremented
- Report: "Library updated: v[N] → v[N+1]. [+X] rules merged, [Y] skipped."

### Step 4: Regenerate project DESIGN.md (optional)

If the developer wants the updated rules in their current project, offer:
"Regenerate project DESIGN.md from updated library? [y/n]"

If yes, re-run Phase 1 Step 3 (generate) with the updated `.ds4a/library.md`.

## Detection Patterns

### Existing design system files to look for

| File | What it contains | Scenario |
|---|---|---|
| `AGENTS.md` | Rules + guardrails in prose | B (has rules) |
| `tokens.json` | Token values (JSON) | B or C |
| `tokens.css` | Token values (CSS variables) | C |
| `src/tokens/tokens.json` | Nested tokens | B or C |
| `src/tokens/tokens.css` | Nested CSS variables | C |
| `globals.css` (shadcn vars) | `--background`, `--primary` oklch | D |
| `design-tokens.ts` / `tokens.ts` | Typed tokens + rich metadata | E (typed pipeline) |
| `global.css` (`@theme` block) | Tailwind v4 theme definitions | E (Tailwind v4) |
| `tokens.generated.css` | Compiled CSS custom properties | E (compiled output) |
| `tailwind.config.js/ts` | Colors, fonts, spacing in JS | C |
| `DESIGN.md` | Already converted | Skip (already initialized) |
| `.ds4a/library.md` | Personal master library | Skip (already initialized) |

### Token extraction from Tailwind v4 `@theme` & TypeScript registries

```css
/* Tailwind v4 @theme in CSS */
@theme {
  --color-lumyra-black: #0a0a0a;  →  colors.black: "#0a0a0a"
  --color-lumyra-accent: #6366f1; →  colors.accent: "#6366f1"
  --font-display: 'Geist';        →  typography.*.fontFamily: "Geist"
  --radius-card: 0.5rem;          →  rounded.card: 0.5rem
}
```

```ts
// TypeScript Token Registry (design-tokens.ts)
export const COLOR_TOKENS = [
  { id: 'lumyra-black', hex: '#0a0a0a', role: 'Primary text', wcag: 'AAA' }
];
// Maps directly to YAML frontmatter with rich roles preserved in Colors prose.
```

### Token extraction from CSS variables

```css
:root {
  --color-primary: #1A5EFF;  →  colors.primary: "#1A5EFF"
  --spacing-xl: 24px;        →  spacing.xl: 24px
  --font-size-label-md: 16px →  typography.label-md.fontSize: 16px
}
```

Map `--color-*` → `colors.*`, `--spacing-*` → `spacing.*`,
`--font-size-*` → `typography.*.fontSize`, `--radius-*` → `rounded.*`,
`--shadow-*` → Elevation prose, `--font-family*` → `typography.*.fontFamily`.

### Token extraction from tailwind.config

```js
colors: { primary: '#1A5EFF' }  →  colors.primary: "#1A5EFF"
spacing: { xl: '24px' }         →  spacing.xl: 24px
fontSize: { md: '16px' }        →  typography.paragraph-md.fontSize: 16px
borderRadius: { sm: '0px' }     →  rounded.sm: 0px
fontFamily: { sans: ['Inter'] } →  typography.*.fontFamily: "Inter"
```

## Pitfalls

- **Dual-Maintenance Token Drift:** In modern web apps with both interactive
  design explorers/docs (requiring JS/TS objects) and Tailwind v4 (requiring CSS
  `@theme`), never maintain both by hand. Designate TypeScript (`design-tokens.ts`)
  or DTCG JSON as the single source of truth, and compile to `tokens.generated.css`
  via a build script on `predev`/`prebuild`. Editing CSS tokens manually leads to
  inevitable divergence between live UI documentation and production styling.

- **AGENTS.md drift:** After migrations (color, radius, typography),
  AGENTS.md prose becomes stale while tokens.json is updated. Always
  discrepancy-check before converting. tokens.json is source of truth for
  values. See `design-system-format-conversion` skill for the full
  discrepancy checklist.

- **Patch operations can delete adjacent lines.** When fixing stale values
  with fuzzy-match, include surrounding context in both old_string and
  new_string. Missing lines = silent data loss.

- **Non-destructive means non-destructive.** Never overwrite AGENTS.md,
  tokens.css, or tailwind.config.js. The DESIGN.md is additive. If the
  developer wants to sync changes back to their original token files, they do
  it manually.

- **Version field is in the library frontmatter.** Not a separate file. On
  merge, increment in-place. No `library-v2.md`, `library-v3.md` junk files.
  The library is one file that grows.

- **No auto-triggering.** The developer types `ds4a init`, `ds4a review`,
  `ds4a merge` explicitly. Don't suggest running review unless asked. Don't
  auto-merge without explicit approval of each suggestion.

- **Taste lock is critical.** The review prompt must read the Overview and
  Do's/Don'ts before outputting suggestions. If a suggestion contradicts the
  aesthetic (e.g., "add rounded corners" for sharp-edge system), discard it
  silently. Do not note that you discarded it.

- **Evidence gating prevents generic output.** No file:line = no
  suggestion. This is the #1 defense against the "review prompt produces
  generic suggestions" failure mode. If you can't point to specific code, you
  can't suggest a rule.

- **Component matrix is a guide, not a law.** If a landing page has a signup
  form, include Input + Field + Button contracts even though the matrix says
  ❌ for Input on landing-page. When in doubt, include rather than exclude.

- **Re-detect from files each session.** Don't store state in memory or
  Honcho. The `.ds4a/` directory tells the skill everything: library.md
  exists = initialized, DESIGN.md exists = generated. This works across
  sessions and for CLI too.
